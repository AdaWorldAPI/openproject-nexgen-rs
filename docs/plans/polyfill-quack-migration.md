## 1. How zammad-rs layers it

### 1.1 rails-polyfill: the write side (in-memory ActiveRecord)

The crate names no application. Its two halves are a runtime and declarative rules (`rails-polyfill/src/lib.rs:1-19`).

- **Store** (`store.rs`). An in-memory row store keyed by column ordinal, with an undo-log transaction model
  (`store.rs:1-8`):
  - `register`, `seed`, `insert`, partial `update`, `delete`, `find`, `where_eq` (equality only), `find_by`
    and `count` (`store.rs:89-387`);
  - nested transactions through `begin`, `rollback` and `release` (`:97-145`);
  - an id allocator, with `next_id` and `reserve_ids` (`:208-220`);
  - NOT NULL checking (`:238-248`).
  - Committed writes can be journaled as `Commit { tables: [TableChange{spec, upserts, deletes}] }`, through
    `journal_commits` and `take_commits` (`:23-36`, `:102-111`, `:154-193`). The journal is what feeds the read side.
- **Record** (`record.rs`). Values by ordinal, dirty tracking (`changes_to_save`, `saved_change`), a `belongs_to`
  cache, and `attr_accessor` virtuals (`record.rs:12-29`, `:120-193`).
- **Lifecycle** (`lifecycle.rs`). The ActiveRecord 8.1 `save` pipeline (`lifecycle.rs:1-12`, `:218-311`):
  - the transaction, then validations, then save/create/update callbacks;
  - timestamps on create and on a dirty update;
  - `after_commit` in declaration order, and `after_rollback`.
  - It also provides `build`, `find`, `find_by`, `where_eq`, `reload`, `save_bang`, `create_bang`, `update_bang`,
    and `belongs_to` / `has_many` navigation (`:153-203`, `:313-418`).
  - **There is no destroy pipeline**: `Action::Destroy => {}` (`:302`). The README says the destroy path is not
    exercised.
- **Callbacks** (`callbacks.rs`). Callbacks are data: `Phase`, `On`, `Cond`, and a `Target`, which is one of
  `Lowered`, `Host`, `Residual`, `Framework` or `Validator` (`callbacks.rs:113-158`). A `Residual` fails the save
  (`:125-127`).
- **Ctx** (`ctx.rs`). Holds the store, the clock `now` (ms), `settings`, `current_user_id`, the callback journal,
  `boundary_log`, and a `Box<dyn Host>` that answers calls leaving the slice (`ctx.rs:37-125`). Because of
  `Box<dyn Host>`, Ctx is not `Send`.
- **Schema types** (`schema.rs:5-14`). `ColumnType` has exactly Integer, String, Text, Boolean, DateTime, Decimal
  and Json. **There is no Date and no Float.** `Value::Time` is milliseconds since the epoch (`value.rs:11-13`).

### 1.2 The generated slice

`zammad-generated` is generated by `rails-compiler` from the Zammad source and `zammad.toml` (59 lines: 10 slice
models, migrations, boundary calls, aliases).
- Each model file has a `col::*` ordinal module, a `TABLE: TableSpec` with `path:line` provenance per column, and a
  `MODEL: ModelSpec` with its linearized callback list (`zammad-generated/src/ticket.rs:1-80`).
- `MODELS` lists them (`zammad-generated/src/lib.rs:17-28`).

For OpenProject, zammad-rs runs **corpus mode only**:
- `openproject.corpus.toml` has `models = []` and `migrations = []`, and it emits nothing;
- `docs/research/semantic-coverage.md:204-235` says no OpenProject behaviour has been executed;
- OpenProject's `load_defaults` is 6.1 (`openproject.corpus.toml`), while the polyfill implements the AR 8.1
  pipeline. `FrameworkDefaults::for_version` (`rules.rs:24-37`) covers three flags.

### 1.3 Quack reads (quack-shadow over lance-graph)

`quack-shadow` answers captured ActiveRecord calls over source-owned column lanes (`quack-shadow/src/lib.rs`
crate doc).

**Catalog.**
- Built from a capture (`Catalog::from_capture`, `:804`) or empty (`Catalog::new`, `:904`), and brought up to date
  by `apply_feed(feed)` (`:959-1037`).
- A feed is `{"tables": {name: {"columns": [...], "upsert": [[...]], "delete": [ids]}}, "relations": ...}`.
- Each table keeps:
  - `u32` lanes plus validity planes for boolean, integer/bigint, timestamp and text columns. `lane_kind` is at
    `:390-402`. Text lanes hold codes into a per-table code table (`Dictionary`, `:1207`).
  - cells for every column without a lane (`Column`, `:235-249`). `date`, `double precision`, `real`, `jsonb` and
    `tstzrange` get no lane *(inferred from `lane_kind`)*.
  - a DR position map (`lance_graph_dt64::dr::MapTable`) and a live plane.

**A call.** A call is the JSON shape the PostgreSQL capture adapter records, for example
`{"table", "terminal": "count"|"exists"|"rows", "where": {"table","col","op","value"} | tree,
"select", "order", "limit", "offset", "joins", "group", "having", "distinct", "from", "lock", "answer"}`
(`oracle/shadow-capture.pg.json`, first call).

**Answers.**
- `answer` returns count or exists (`:2840-2866`).
- `rows` returns `RowsAnswer { columns, rows, ordered, ties, kept, materialized, join }` (`:3027-3060`, `:2428-2444`).
- The WHERE lowers to a `lance_graph_quack::Query` and runs through `lance_graph_mask_risc::execute_into`
  (`:2765-2838`).
- The verdict functions compare with the recorded `answer`: `verdict`, `rows_verdict` and `shadow_verdict`
  (`:2869-3240`).
- Anything inexpressible is refused by name. `Refusal` (`:2325-2408`) includes joins outside the star shape,
  GROUP/HAVING/DISTINCT, row locks, ORDER BY on text (`TextOrder`), unordered LIMIT, ties at the limit, unlaned
  filter columns, `UncommittedRead` (`dirty_tables`), and `Unrenderable` for `timestamp with time zone` (`:2393-2399`).

**How zammad-desk uses it.**
- `Desk` holds a `rails_polyfill::Ctx`, a `quack_shadow::Catalog` and the `unfed: Vec<Commit>` queue (`zammad-desk/src/lib.rs:532-544`).
- Writes go through `lifecycle::build` and `lifecycle::save` on the generated `ModelSpec` (`:1121-1145`).
- Committed writes become feeds through `zammad_parity::feed::feed_json(&Commit)` (`zammad-parity/src/feed.rs:118`;
  its doc, `:1-9`, says it lives there so the polyfill carries no wire format), which are handed to
  `catalog.apply_feed` (`deliver`, `zammad-desk/src/lib.rs:1081-1095`).
- Display reads are `quack_shadow::rows(&catalog, &call, false)` with a hand-built call
  (`read` / `read_all`, `:2098-2195`; used by `tickets_for`, `customers_of` and `ticket_detail`).
- Consistency reads inside a write (lookups, state and group rows) go straight to the write-side store
  (`ctx.store.where_eq` / `lifecycle::find_by`, for example `:1584-1610`).
- Note: `quack-shadow` depends on `rails-f000` (`quack-shadow/Cargo.toml`, `src/bound.rs:24-64`).
  `rails-f000` depends on `rails-compiler`, ruff, OGAR and `zammad-generated` (`rails-f000/Cargo.toml`).

### 1.4 Persistence: the state directory

`zammad-ticket/src/store.rs:1-12`:
- `<dir>/base.json` holds a `Desk::snapshot()`;
- `<dir>/records/<seq:020>.json` holds one record per committed write: `{"seq", "now", "feed", "desk": {...}}`
  (`zammad-desk/src/lib.rs:867-883`);
- every file is written atomically (temp file, fsync, rename, directory fsync; `store.rs:106-125`);
- a lock file holds out a second writer (`:139-179`).

Startup and the write path:
- **Load** (`:191-260`): build from `base.json` if present, else from the seed. Then `replay` every record in
  sequence. A gap, a torn file or a foreign file refuses the start.
- **Replay** writes rows with callbacks off and journaling off, and feeds the catalog (`zammad-desk/src/lib.rs:891-1021`).
- **Writes** are acknowledged only after their record is on disk. A failed write rebuilds the desk from disk
  (`zammad-ticket/src/service.rs:230-336`, `finish_write`).
- **Compaction** rewrites the base and removes the records it covers (`compact_if_due`, `:273-295`).
- **Threading.** `Desk` is not `Send` and lives on one dedicated thread; `Tickets` sends messages with oneshot
  replies (`service.rs` crate doc, lines 1-15).
- **Railway.** A volume is mounted at `/state` with `TICKET_STATE_DIR=/state` (`zammad-ticket/deploy/railway.ts`,
  marked not active).

### Gaps with no zammad-rs precedent, or no support at all

1. **Column types.**
   - `rails-polyfill::ColumnType` has no Date and no Float (`schema.rs:5-14`), and `Value` has no Date variant
     (`value.rs:15-30`). nexgen needs `date` (start_date, due_date, non_working_days) and `double precision` /
     `real` (estimated_hours, remaining_hours, derived_*).
   - `zammad-parity::feed::sql_type` / `cell` (`feed.rs:23-34`, `:72`) spell only the seven polyfill kinds.
   - The fix is an upstream PR to zammad-rs adding `ColumnType::{Date, Float}` and `Value::Date`, plus feed
     rendering. Alternatively, nexgen keeps dates as `Int` days and floats as `Decimal` (lossy, and visible in
     parity).
2. **`timestamptz`.**
   - nexgen's schema uses `timestamptz` (37 columns), and Quack refuses rendering `timestamp with time zone`
     (`Refusal::Unrenderable`, `lib.rs:2393-2399`).
   - Option a: the polyfill feed declares `timestamp(3) without time zone` (as zammad-parity does for every
     DateTime, `feed.rs:30`), so PostgreSQL stays the oracle while the runtime is UTC-naive.
   - Option b: wait for Quack to render offsets.
3. **Precision.** The polyfill keeps ms (`value.rs:11-13`). The journal rule uses `+ interval '1 microsecond'`
   (`mutation.rs` ~`:2093-2106` by grep). In ms the closing bound becomes +1 ms, so the parity test must compare
   these timestamps at ms, or µs must be added.
4. **`tstzrange` and `jsonb`.** `journals.validity_period` and `journals.cause`.
   - Map `cause` to `ColumnType::Json` (text).
   - Map `validity_period` to either two DateTime columns (`validity_lower`, `validity_upper`) in the polyfill
     schema, with the Postgres oracle projected to `lower()` / `upper()`, or a Json text cell.
   - This is a design decision.
5. **Optimistic locking (`lock_version`).** Not in the polyfill. Either nexgen code compares `lock_version` before
   `save` and sets `lock_version + 1` (application code over the store), or a rule is added upstream to
   `rails-polyfill` (`R-LOCKING-OPTIMISTIC`). The second is the zammad-rs way, and it needs an oracle case.
6. **Destroy.** The polyfill has no destroy pipeline. Work-package delete in OpenProject has destroy callbacks
   (journals, relations, watchers, children) *(inferred; not read in OP)*. nexgen today does a bare
   `DELETE` (`op-db/src/work_packages.rs`, `delete`). Keep `Store::delete` with the same bare semantics and
   record the divergence, or extend the polyfill.
7. **Joins on the read side.** Quack joins are a star with declared relations, no ORDER BY (`Refusal::JoinOrder`,
   `JoinShape`). The API representers that embed linked names (status name, project name) already resolve them
   with separate lookups in `board.rs:618-680`. Keep separate calls.
8. **Text sorts and LIKE.** Text ORDER BY is refused (`TextOrder`). LIKE exists (`sql.rs`, `LikeStats`; not read).
   API sorts by `subject` / `name` must sort in Rust after `rows`, or stay refused.
9. **An OpenProject slice** (generated `ModelSpec`s).
   - `rails-compiler` reads the schema from the configured migrations (`rails-compiler/src/lib.rs:360`,
     `schema.rs:111`). OpenProject's baseline migrations are not configured anywhere.
   - OpenProject is `load_defaults 6.1` against an AR 8.1 pipeline.
   - The nexgen schema is hand-written and differs from OpenProject's (no hierarchies table).
   - Smallest path: hand-declare `TableSpec`s matching nexgen's migrations, with empty `callbacks`, behind a
     module shaped like a generated one, and move to compiled specs later.
10. **Dependency weight.** `quack-shadow` pulls `rails-f000` → `rails-compiler`, ruff, OGAR and `zammad-generated`
    into any binary that uses it. zammad-ticket already ships that way. For nexgen this means `zammad-generated` in
    the OpenProject binary. Upstream remedy: split `quack-shadow`'s binding (`bound.rs`) from the catalog, or move
    `feed.rs` and the catalog into a generic crate.
11. **Single writer vs. async multi-threaded axum.** Ctx is not `Send` (`Box<dyn Host>`). The nexgen store traits
    are `async fn` without `Send` bounds (`#[allow(async_fn_in_trait)]`, `mutation.rs:194`), so a desk-handle impl
    can await a oneshot. All writes serialize through one thread, as in zammad-ticket.
12. **No settings table.** nexgen constants already stand in for settings (`mutation.rs:44-63`). They map to
    `Ctx.settings`.

## 4. Making SQLx oracle-only

What stays (oracle, dev-only):
- `op-db` migrations and repositories, used only by the oracle capture and tests. They move behind a
  `[dev-dependencies]` / feature `pg-oracle` and leave `op-server`'s runtime dependencies.
- `EXECUTED_DB`, kept as is (it is the live-Postgres witness of today's semantics), plus a **capture mode**: the
  same journey writes `oracle/executed-db.pg.ndjson`. The file holds, per step:
  - the inputs (caller, params, clock);
  - the outcome (Ok row / error kind);
  - the committed row images of every touched table, read back with SQL, in the polyfill feed shape
    (`{"tables": {name: {"columns", "upsert", "delete"}}}`);
  - the answers of the reads the step made (rows / count).
  This is the same artifact class as zammad-rs's `shadow-scenario*.pg.ndjson`.
- A new replay test (no database needed) runs the same journey against the polyfill desk. It asserts:
  - the step outcomes are equal;
  - the write-side store's rows equal the captured rows, modulo a declared column map (validity_period split,
    ms precision);
  - every recorded read answered through `quack_shadow::rows` equals the recorded answer, or is refused by name
    with exact counts (the `parity.rs` style, `quack-shadow/tests/parity.rs:30-90`).
- `oracle/work_package_service.rb` traces stay the behaviour oracle against OpenProject itself, compared with the
  polyfill journal where callbacks are compiled.
- A CI job `pg-oracle` (with `OP_TEST_DATABASE_URL`, `REQUIRE_DB=1`) regenerates the capture and fails on a byte
  diff, so the recorded file cannot drift from real PostgreSQL.

Removed from runtime:
- `sqlx` from `op-server`, `op-api`, `op-services` and `op-models` runtime dependencies;
- `Database::connect` / `run_migrations` / `seed_kanban` from `main.rs`;
- `PgMutationStore` / `PgCreateScope` / `PgWpStore` (moved to the oracle crate or deleted after parity);
- the Postgres plugin and `DATABASE_URL` from `railway.toml`.

## 6. Risks and open decisions for the owner

1. **Which schema is canonical:** nexgen's hand-written migrations or OpenProject's own? The PG oracle today runs
   nexgen's schema, so parity proves "same as today's SQL port", not "same as OpenProject". The Ruby oracle is the
   only OpenProject-faithful witness.
2. **Upstream changes to zammad-rs** (Date / Float types; optimistic locking; possibly destroy; splitting
   `quack-shadow`'s dependency on `rails-f000`): accept them as zammad-rs PRs, or encode locally in nexgen?
3. **`timestamptz` vs `timestamp(3)` and ms vs µs:** accept a declared divergence in the parity map, or require
   exact µs?
4. **`validity_period` (tstzrange) and `cause` (jsonb) representation** in the polyfill schema.
5. **Where `feed_json` lives:** depend on `zammad-parity` (Zammad-named), copy it, or extract a generic crate
   upstream?
6. **The dependency weight of `quack-shadow`** (pulls `zammad-generated`, `rails-compiler`, ruff and OGAR into the
   nexgen binary). Acceptable, or split first?
7. **Single-writer throughput.** One thread serializes every write, and reads too if they go through the same
   handle. zammad-ticket accepts this. Should reads share the thread or get a read-only catalog clone?
   *(Design choice; zammad-ticket answers reads on the desk thread.)*
8. **No Cargo.lock and git `branch = "main"`** for zammad-rs and lance-graph. Any upstream push can break nexgen
   builds. Pin revisions?
9. **Text sorts and date filters refused by Quack.** The API keeps returning them sorted in Rust, or reports a
   refusal? This changes API behaviour if left refused.
10. **Railway data migration:** the live Postgres instance's rows (if any real data exists) must be exported once
    into the seed / base JSON. PR 3's capture writer can produce `base.json` from a live database.
11. **Seed:** `kanban_seed.sql` vs. a JSON seed; `HYDRATE=1` semantics change.
12. **Delete semantics:** a bare delete (today) vs. OpenProject's destroy behaviour.
